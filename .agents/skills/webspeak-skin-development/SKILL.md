# WebSpeak skin development

Use this skill when editing or authoring a WebSpeak `.wskin` package, a built-in skin, or skin-facing UI hooks. v1/v2 packages are visual/layout data; v3 may compose bounded declarative UI from its own nodes, rearrange public UI, and replace the visible home/voice page with a validated surface. v4 adds approved runtime plugins: bounded Wasm runs in a disposable worker and emits a validated generic HTML/SVG node tree; plugin-local CSS and scalar UI state are supported. JavaScript files remain validated and cached, never executed. Optional host widgets are trusted primitives, not the limit of custom UI. WebSpeak owns TeamSpeak behavior and the administrator console is outside the skin scope.

## Before editing

- Read [`docs/SKIN_DEVELOPMENT.md`](../../../docs/SKIN_DEVELOPMENT.md) for the current package validator and public hooks.
- Use [`docs/examples/illusia-voice/`](../../../docs/examples/illusia-voice/) and [`docs/examples/ILLUSIA-VOICE.md`](../../../docs/examples/ILLUSIA-VOICE.md) as the reference implementation. Do not restore the removed Aurora Voice sample.
- Inspect the actual component markup for `data-ws-page`, `data-ws-part`, and `data-ws-state` hooks. Treat Vue classes and incidental DOM structure as private.

## Preserve the interface

- Keep WebSpeak's translations and semantic content as the baseline. Add `content.json` only when a text override is an explicit part of the request; never use it to implement visual artwork.
- Follow the schema-specific CSS rules: v1/v2 reject layout changes; v3 allows layout, placement, size, typography, and visibility changes within the skin root. Keep CSS package-local, scoped to public hooks, and free of external resources or executable values. Do not describe v3's fixed element, attribute, data, and action registries as complete customization; the target is a versioned, isolated plugin runtime with author-owned UI structure, CSS, and local logic.
- v3 can replace or obscure normal page controls. A surface must request `ui.surface.replace` and stays disabled until the user approves it. Custom interfaces can use their own declarative nodes and CSS; embed optional host widgets only when a trusted WebSpeak control is useful. Available widget IDs are registered in `src/shared/skin-plugin.ts`; each stateful host widget may appear once per page. Preserve usable microphone, disconnect, device-settings, screen-share and recovery paths at desktop and mobile sizes. Verify both the return-to-built-in-UI and restore-built-in-skin buttons. The host recovery and permission UI render outside the skin root. Keep `/admin/**` unskinned.
- `components.json` schema v1 is legacy; v2 adds `mode: "surface"` and optional allowlisted host-widget nodes; v3 expands bounded declarative composition, data bindings, events and permission-gated voice actions. v3 keeps its fixed tag/attribute/data/action registries; use v4 when a skin needs its own UI logic or generic HTML/SVG tree.
- For full-page custom interfaces, author the messages, composer, channel selection, audio controls and member presentation as skin-owned nodes wherever the safe data/action API supports them. Treat host widgets as optional trusted leaves for capabilities that must remain inside WebSpeak, such as screen capture and live media playback. Schema v3 conditions may compare local state with a permissioned repeated item and render explicit empty states; host actions may run on committed `change`, submit, or explicit activation, while live `input` remains local-only.
- The v4 runtime is enabled in production for Wasm only. A plugin must pass the local digest-bound approval before a disposable worker starts. The module has a 256 KiB source cap, 4 MiB linear-memory cap, 10,000,000 fuel cap, 100 ms execution deadline and a 64 MiB interpreter container cap; the WebClient governor allows two active jobs, up to 64 pending jobs, and a 120-second queue deadline. Each job may emit one UTF-8 JSON UI document of up to 256 KiB. The host validates schema v3/v4/v5/v6 and renders nodes itself; it never inserts plugin HTML. Standard tags and scalar attributes are allowed within size limits. Script, embedded browsing, navigation/external resource attributes, inline `style`, event-handler attributes and dangerous elements are rejected. Custom element names become inert `div` placeholders, so page-registered Web Components do not run.
- `env.ui_input_read` supplies at most 64 KiB per run, including plugin-local scalar state, a safe event record and a public-data projection capped at 48 KiB. The projection contains only fields permitted by the plugin manifest; never pass TeamSpeak addresses, credentials, SDK objects, media streams or private application objects. `ui.input.read` is a separate opt-in for text and checkbox/select values; tell users that browser autofill may be included, and never request password/file/hidden values. Keep server-list labels and opaque identifiers separate from addresses and credentials. Use `servers.quickList` plus `quickServers.switch` when a custom UI should show favorites and recent servers together.
- Host actions can be requested only by a run caused by a real browser-trusted UI event. The host rechecks the plugin grant, action permission, arguments and current session; a guest cannot supply its own trust flag. The first bridge permits one action per event run. Async Wasm cannot be assumed to preserve transient user activation: use the trusted `voice.screen-share-start` host widget for screen capture. Host widgets execute in WebSpeak and do not grant author code access to private widget state.
- The v4 package parser is shared by client import and server registration. It accepts `plugins.json` schema v1 with local `plugins/<id>/` JS/Wasm/CSS/assets, a 256 KiB descriptor cap, 256 KiB entry cap, 512 KiB CSS cap and 32 assets per plugin. It supports widget/surface modes and semantic mount slots. Plugin CSS is compiled under the plugin component scope; the host consent and recovery controls stay outside that scope. v4 plugin roots, components and DOM nodes participate in local layout editing. Keep v1–v3 unable to reference executable files. Cross-browser end-to-end validation and independent security review remain outstanding; marketplace and dedicated plugin-management UX are deferred with the administrator-panel redesign.
- Use the host's reserved artwork hooks for layered character art and the headphone scene. Prefer transparent assets and `background-size: contain` where the reference requires the full character or chibi to remain visible; arrange the artwork around the fixed hook rather than changing its geometry.
- Build visual depth with separate background, surface, and foreground artwork already exposed by the hooks. Avoid duplicate static decorations when an animated replacement exists. For motion, keep waveforms/sonar smooth and restrained, honor reduced-motion preferences, and retain readable focus, error, mute, and speaking states.
- Keep skin-specific CSS variables under `--skin-*`. Use only package-local assets and confirm their redistribution rights.

## Verify and package

1. Compare the implementation with its accessible visual reference at desktop and narrow widths. Check the homepage, voice workspace, empty chat, member list, screen-share player, selectors, and `/demo`; verify no crop, overflow, text collision, or control overlap. Record exactly which reference pages and states were observed; do not imply that unvisited pages or states were verified.
2. Check all five interface languages, day/night modes, keyboard focus, and reduced-motion behavior. Confirm the admin console is unchanged.
3. Run the relevant skin-package tests and application build after a related batch of changes. Fix validation failures rather than weakening v1/v2 boundaries, v3 permission and event checks, surface limits, or the host-widget allowlist.
4. Package the contents of the skin directory so `manifest.json` is at the archive root, then import it through `/admin/skins` and retest the installed `.wskin` in a visitor session.

Keep README files beside the package source instead of inside `.wskin`: the skin importer rejects undeclared files such as `README.zh-CN.md`.

The shipped default day, default night, and ILLUSIA skins are protected built-ins. Do not change their IDs or introduce upload/update flows that can disable, replace, or remove them. A permission request is not a grant; verify the deny and revoke paths. Do not claim a skin was visually verified against an external reference unless that page was actually accessible.

## Current project sequencing

- The user has explicitly set the order: finish and stabilize the generic skin authoring system before implementing a reference skin. Do not keep browsing reference pages or redesigning the framework during skin implementation.
- The public-client component editor stores authoring overrides in per-skin/per-version local-storage keys. A malformed document must not render; allow that one version's saved edit to be cleared without disturbing other skins. Route every import and edit through the shared declarative component parser; never weaken the tag/attribute, data-path, permission, action, or host-widget checks to make an edit fit.
- Treat data-ws-* as host-reserved DOM metadata: preserve backward parsing of older skin packages, but strip those attributes at the rendering boundary and reject them in new authoring saves.
- Component-tree CRUD includes component creation, duplication, deletion and ordering; node creation, duplication, deletion and sibling ordering; JSON property edits; undo/redo; and components.json import/export. Give duplicated nodes fresh stable layout-part identifiers. Preserve a usable base page and host recovery controls when a custom surface is removed.
- Before beginning the reference skin, verify tree CRUD, empty documents, safe schema migration, version-scoped persistence, import/export round trips, rejection of unsafe/over-permissioned trees, skin/page switching, and recovery. Run the related tests and server/client builds as one batch, then retain a stable checkpoint.
- Once that gate passes, only make small framework fixes for concrete incompatibilities found while implementing the voice-only reference. Do not expand unrelated application code or repeat visual-reference collection without a specific unresolved question.

## Integration findings

- A full-page surface is a separate user-approved capability (`ui.surface.replace`); package installation alone must leave the built-in page visible.
- The “restore built-in skin” control must use an unconditional selection function, not the skin-load-error-only recovery handler.
- Custom quick-server layouts should use the unified favorites/recent collection and opaque host tokens. Labels that match the underlying address are redacted before projection; never expose target addresses or credentials to skin data bindings.
- KOOK voice-only visual reference: the first two user-authorized rooms were accessible in the in-app browser. Observed voice membership nested under the channel tree, the lower-left connection card with screen-share and audio controls, and the persistent central chat/right member panes. Microphone remained off and the client was disconnected after inspection. No server/room identifiers, member names, or chat content were retained. Keep discovery, events, companion shop, ads, and operator/admin surfaces out of this skin.
- Report the exact system constraints discovered during implementation in both the roadmap and this skill. Keep each step reversible: preserve a clean tested checkpoint before changing package/runtime protocol versions, do not rewrite or push history without an explicit request, and keep v1/v2/v3 behavior isolated from new plugin capabilities.
